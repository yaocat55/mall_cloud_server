## #1 [P0] 缺少定时关单 Job

**文件**: 新建 `mall-pay/.../job/PayOrderCloseJob.java`

**现象**: Nacos 配置了 `mall.pay.order.close-scan-interval-minutes: 10`，但没有对应的定时任务。`PayCoreService` 已有关单查单方法但无调度入口。

**影响**: 过期支付单（超过 30 分钟未支付）永远不会自动关闭。用户重新支付时 create 的幂等逻辑会返回已有待支付单，导致用户无法重新发起支付。

**修复方案**:
1. 新建 `PayOrderCloseJob`，表达式 `${mall.pay.order.close-scan-cron:0 */10 * * * ?}` 每 10 分钟
2. 扫描条件：`pay_status = 10 AND create_time < NOW() - expire_minutes`
3. 关单后调渠道 close，标记状态 30
4. 关单后发送 MQ 通知业务方（见 #5）

## #2 [P0] `queryUnpaidOrders` 无时间过滤 + 无分页

**文件**: `mall-pay/.../service/PayCoreService.java:142`

**现象**:
```java
// 当前代码：扫描所有 WAIT_PAY 订单，没有任何时间条件
PayOrderConditionEntity condition = new PayOrderConditionEntity();
condition.setPayStatus(PayStatusEnum.WAIT_PAY.getValue());
List<PayOrderEntity> waitingOrders = payOrderService.searchByPage(condition).getData();
```
- 配置了 `query-after-minutes: 5` 但代码完全没用
- 刚创建 1 秒的订单也去查微信/支付宝，浪费渠道 API 配额
- 没有分页限制，订单量大时直接 OOM

**影响**: 查单兜底形同虚设——全部扫一遍浪费资源，真正需要查的（已过 5 分钟无回调的）反而可能被淹没。

**修复方案**:
1. 条件加上 `create_time < NOW() - ${mall.pay.order.query-after-minutes} min`
2. 条件加上 `create_time > NOW() - ${mall.pay.order.expire-minutes} min`（已过期的关单处理，不查）
3. 设置 `pageSize` 限制单次扫描量（如 100），配合调度频率覆盖全量

## #3 [P1] `retryFailedNotifications` 无调度

**文件**: `mall-pay/.../service/NotifyService.java:73`

**现象**: 方法注释写明"定时扫描发送失败的支付通知，退避重推"，但没有 `@Scheduled` 注解。

**影响**: `sendPaySuccessNotify()` 如果 MQ 发送失败（bizNotifyStatus=2），永远不会自动重试。业务方收不到支付结果，只能靠次日对账发现。而接入指南明确写了"MQ 发送失败会标记 → 定时任务退避重推"——属于文档承诺了但代码没实现。

**修复方案**:
1. 新建 `NotifyCompensateJob`，表达式 `${mall.pay.notify-compensate.cron:0 */1 * * * ?}` 每分钟
2. 扫描 `biz_notify_status = 2 AND notify_count < 5` 的订单
3. 退避逻辑已有（NotifyService.retryFailedNotifications 里的次数判断），直接复用

## #4 [P1] `handleNotify` 无 DB 乐观锁

**文件**: `mall-pay/.../service/PayCoreService.java:217`

**现象**:
```java
// 当前：只在 Java 层判断状态
if (!PayStatusEnum.WAIT_PAY.getValue().equals(order.getPayStatus())) {
    return;
}
// ... 直接 update，没有 WHERE pay_status = 10
payOrderService.update(order);
```
- 如果支付宝/微信并发回调（虽然少见但微信确实会重试），两次回调可能都通过 if 检查
- `PayOrderMapper.xml` 的 update SQL 没有 `WHERE pay_status = 10` 条件

**影响**: 并发回调时小概率重复处理（两次 sendPaySuccessNotify），业务方需做好幂等（接入指南也强调了幂等）。当前影响可控但不够严谨。

**修复方案**:
1. `PayOrderMapper.update` 改为带 version 乐观锁或 `WHERE pay_status = 10` 的 CAS update
2. 或者新增 `updatePayStatus` 专用方法：`UPDATE pay_order SET pay_status=20, ... WHERE id=? AND pay_status=10`
3. 如果受影响行数 = 0，log 警告但不抛异常（幂等，返回 success 即可）

## #5 [P2] 关单后不通知业务方

**文件**: `PayCoreService.closeOrder()` + `PayCoreService.queryUnpaidOrders()`

**现象**: 关单只是本地状态 10→30，没有 MQ 通知业务方。业务方（如 mall-order）不知道支付单已关闭，订单侧库存仍然冻结。

**影响**: 库存永久冻结直到订单侧自己超时取消。短期可依赖订单侧的超时取消兜底，但支付侧独立运行时（其他业务方接入）就是硬伤。

**修复方案**:
1. 新增 `NotifyService.sendPayClosedNotify(order)` 方法，发送 CLOSED 类型通知
2. `closeOrder()` 和 `queryUnpaidOrders()` 关闭订单时调用
3. 业务方 MQ 消费者监听 CLOSED 事件释放资源

## #6 [P2] `PayInternalController` 无认证

**文件**: `mall-pay/.../controller/internal/PayInternalController.java`

**现象**: 内部 Feign 接口（`/v1/internal/pay/**`）没有任何认证机制，网关不暴露但服务网格内任意 Pod 可直接调用。

**影响**: 依赖网络层隔离（网关不暴露 /internal/**），在 K8s 环境下同集群内任意容器可调用。短期可接受，长期需加内部 JWT 或 mTLS。

**修复方案**:
1. 短期：网关层配置 `/v1/internal/**` 拒绝外部访问
2. 长期：加内部服务间 JWT 或 Spring Security 内部角色校验
