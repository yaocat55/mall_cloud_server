# 鉴权架构与信任链路

## 概述

全系统采用 **JWT 无状态鉴权**，Gateway 统一验签后透传身份，后端服务独立验证，不信任上游 Header。

---

## 一、鉴权组件清单

### 1.1 核心组件（mall-auth-api-starter）

通过 Spring Boot `AutoConfiguration.imports` 自动注入到所有 Servlet 服务（10 个）。

| 类 | 类型 | 作用域 | 职责 |
|----|------|--------|------|
| `AuthApiInterceptor` | `HandlerInterceptor` | 所有 HTTP 请求 | JWT 验证 + 设置 SecurityContext |

| `AuthApiConfigurer` | `WebMvcConfigurer` | — | 注册拦截器到全部路径 |

**覆盖的服务：**

| 服务 | 模块 | 依赖 starter |
|------|------|:------------:|
| mall-admin | 管理后台 API | ✅ |

| mall-customer | C 端用户服务 | ✅ |

| mall-message | 消息服务 | ✅ |

### 1.2 专属组件

| 类 | 所在服务 | 类型 | 职责 |
|----|---------|------|------|
| `AuthFilter` | **mall-gateway** | `GlobalFilter`（WebFlux） | JWT 验签，覆写 X-User-* 头 |

## 二、完整鉴权流程

### 2.0 HTTP 请求示例概览

以下通过一组连续的 HTTP 请求/响应示例，展示一个管理员登录后查询订单列表时，每个组件看到的实际报文。

#### 前置：客户端登录

```http
// ===== 请求 =====
POST /api/admin-api/v1/auth/web/user/login HTTP/1.1
Host: api.mall.com
Content-Type: application/json

{
  "username": "admin",
  "password": "********"
}

// ===== 响应 =====
HTTP/1.1 200 OK
Content-Type: application/json

{
  "code": 200,
  "data": {
    "token": "eyJhbGciOiJIUzUxMiJ9.eyJ1c2Vy...zN0In0.abc123..."
  }
}
```

#### 步骤 1：客户端 → Gateway（携带 JWT 请求业务接口）

```http
// ===== 请求 =====
GET /api/order/v1/admin/order/page?page=1&size=10 HTTP/1.1
Host: api.mall.com
Authorization: Bearer eyJhbGciOiJIUzUxMiJ9.eyJ1c2Vy...zN0In0.abc123...

// ===== Gateway AuthFilter 看到的内容 =====
// Authorization: Bearer eyJhbG...  ← 原始 token
// X-User-Id: （无，客户端没传，传了也会被覆盖）
// 无其他身份头
//
// AuthFilter 验签通过后，mutation：
```

#### 步骤 2：Gateway → mall-order（AuthFilter 验签后透传）

```http
// ===== 实际透传到 mall-order 的请求 =====
GET /v1/admin/order/page?page=1&size=10 HTTP/1.1            ← StripPrefix=2 去掉了 /api/order
Authorization: Bearer eyJhbGciOiJIUzUxMiJ9.eyJ1c2Vy...zN0In0.abc123...  ← ★ 保留原 token
X-User-Id: 13                                                ← AuthFilter 写入
X-User-Name: admin                                           ← AuthFilter 写入
X-Roles: admin                                                ← AuthFilter 写入

// ===== mall-order AuthApiInterceptor 处理 =====
// 同时有 X-User-Id + Authorization → 双校验
//   1. 解析 JWT → claims.user_id = 13
//   2. 比对 X-User-Id: 13 → 一致 ✅
//   3. 以 JWT claims 为准 → setSecurityContext
// 校验通过，进入 Controller
```

#### 步骤 3：微服务 → Feign → 依赖服务（FeignAuthInterceptor 透传）

```http
// 微服务 Controller 调用 FeignClient：
// orderFeignClient.listOrders(page, size);

// ===== FeignAuthInterceptor 处理 =====
// 从当前线程 RequestContextHolder 取到 Authorization:
//   → "Bearer eyJhbGciOiJIUzUxMiJ9..."

// ===== 实际发出的 Feign HTTP 请求 =====
POST /v1/internal/trade/list HTTP/1.1                         ← Feign 调用
Authorization: Bearer eyJhbGciOiJIUzUxMiJ9.eyJ1c2Vy...zN0In0.abc123...  ← FeignAuthInterceptor 透传
INNER-REQUEST: true                                           ← FeignAuthInterceptor 标记
Content-Type: application/json

{"page":1, "size":10}

// ===== 后端服务 AuthApiInterceptor 处理 =====
// 有 Authorization → 无 X-User-Id 头 → 走 JWT-only 分支
//   1. 解析 JWT → claims.user_id = 13
//   2. setSecurityContext(claims)
// 校验通过，进入 Controller
```

#### 步骤 4：伪造攻击示例（内网直调）

```http
// ===== 攻击者直调后端服务，伪造身份头 =====
POST /v1/internal/trade/list HTTP/1.1
X-User-Id: 13
X-User-Name: admin
X-Roles: admin
Content-Type: application/json

{"page":1, "size":10}

// ===== AuthApiInterceptor 看到 =====
// 有 X-User-Id → 检查 Authorization → 无 JWT
// → 响应 401：{"error": "缺少有效的 JWT"}
// ✗ 拒绝，防御成功
```

#### 步骤 5：伪造攻击示例（Header 与 JWT 不一致）

```http
// ===== 攻击者获取了普通用户 JWT，尝试提权 =====
GET /v1/admin/order/page?page=1&size=10 HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzUxMiJ9.eyJ1c2Vy...普通用户...abc123...
X-User-Id: 13
X-User-Name: admin
X-Roles: admin

// ===== AuthApiInterceptor 看到 =====
// 有 X-User-Id + Authorization → 双校验
//   1. 解析 JWT → claims.user_id = 42（普通用户）
//   2. 比对 X-User-Id: 13 ≠ claims.user_id: 42 → 不一致
// → 响应 401：{"error": "JWT 身份与请求头不匹配"}
// ✗ 拒绝，防御成功
```

### 2.1 外部请求（客户端 → Gateway → 微服务）

```
客户端
  │  Authorization: Bearer <JWT>
  ▼
┌─────────────────────────────────────────────────┐
│ Gateway (WebFlux)                                │
│                                                  │
│  AuthFilter.filter():                            │
│    1. 匹配白名单 → 是 → 放行（不验 JWT）          │
│    2. 有 JWT → Jwts.parser().verifyWith() 验签    │
│       ├─ 通过 → mutate 请求，添加 Header:         │
│       │   X-User-Id    ← claims.user_id           │
│       │   X-User-Name  ← claims.user_name         │
│       │   X-Roles      ← claims.roles              │
│       │   ★ 保留原始 Authorization 头              │
│       │   → chain.filter()                         │
│       └─ 失败 → 返回 401                           │
│    3. 无 JWT → 返回 401                            │
└──────────────────┬──────────────────────────────┘
                   │  Authorization + X-User-*
                   ▼
┌─────────────────────────────────────────────────┐
│ mall-order (Servlet)                            │
│                                                 │
│  AuthApiInterceptor.preHandle():                │
│    1. 有 Authorization → 解析 JWT               │
│       → setSecurityContext(claims)             │
│    2. 无 Authorization → 放行（公开接口）       │
│                                                 │
│  SpringSecurityConfig (mall-order):             │
│    /v1/admin/**   → authenticated              │
│    /v1/mobile/**  → permitAll                  │
└──────────────────┬──────────────────────────────┘
                   │  Authorization（经网关透传）
                   ▼
┌─────────────────────────────────────────────────┐
│ 后端服务 (Servlet)                                │
│                                                  │
│  AuthApiInterceptor.preHandle():                 │
│    同上逻辑：JWT 为最终信任源，不信任 Header        │
│                                                  │
│  (mall-admin 额外) JwtTokenFilter.doFilter():    │
│    1. 有 token → 解析 JWT                        │
│    2. 查 Redis blacklist:<jti>                   │
│       ├─ 在黑名单 → 401 "token 已被踢下线"        │
│       └─ 不在 → setSecurityContext + 继续         │
│    3. 无 token → 放行                            │
│                                                  │
│  SpringSecurityConfig (mall-admin):              │
│    /v1/internal/**  → permitAll                   │
│    /v1/web/**       → permitAll                   │
│    其他            → authenticated               │
└─────────────────────────────────────────────────┘
```

### 2.2 Feign 内部调用（微服务 → 依赖服务，无 Gateway 参与）

```
微服务 Controller
  │  Authorization: Bearer <JWT>
  ▼
FeignAuthInterceptor
  │  从 RequestContextHolder 取 Authorization
  │  写入 Feign 请求头
  ▼
依赖服务 AuthApiInterceptor
  │  解析 JWT，独立验签
  │  不依赖 X-User-* 头
  ▼
  setSecurityContext(claims)
```

> ⚠️ 微服务的 `AuthApiInterceptor` 在收到 Gateway 透传的 `X-User-*` 头 + `Authorization` 头时做双重校验。如果微服务自己发起 Feign 调用且需要身份，FeignAuthInterceptor 负责透传 Authorization 头。

### 2.3 FeignAuthInterceptor 透传详解

```java
// FeignAuthInterceptor.apply()
public void apply(RequestTemplate template) {
    // 1. 从当前线程的请求上下文取 Authorization 头
    RequestAttributes requestAttributes = RequestContextHolder.getRequestAttributes();
    if (Objects.isNull(requestAttributes)) {
        return;  // 没有请求上下文（定时任务、MQ 消费者等）
    }

    ServletRequestAttributes servletRequestAttributes =
            (ServletRequestAttributes) requestAttributes;
    HttpServletRequest request = servletRequestAttributes.getRequest();
    String authorization = TokenUtil.getAuthorization(request);

    // 2. 有 token 则透传
    if (StringUtils.hasLength(authorization)) {
        template.header(AUTHORIZATION, authorization);
    }
    // 3. 标记为内部请求
    template.header(INNER_REQUEST, "true");
}
```

**数据流：**

```
Gateway 透传 (保留 Authorization)
       │
       ▼
微服务 Controller (有 RequestContextHolder)
       │
       ├── FeignAuthInterceptor 读取 Authorization
       │        ↓
       │   Feign 调用 → Authorization 头 → 依赖服务
       │
       └── 无同步请求上下文时（如 @Async、MQ）
               ↓
           interceptor 直接 return
           下游无 Authorization → 后端视为无身份请求
```

**局限：**

| 场景 | 是否透传 | 说明 |
|------|:--------:|------|
| Feign 在控制器线程内 | ✅ | `RequestContextHolder` 有值，正常透传 |
| Feign 在异步线程（`@Async`） | ❌ | 无请求上下文，不会透传 |
| Feign 在定时任务（`@Scheduled`） | ❌ | 无请求上下文，不会透传 |
| Feign 在 MQ 消费者 | ❌ | 无请求上下文，不会透传 |

如果出现后三种场景需要身份，需要手动传 JWT 参数，不能用自动透传。

### 2.4 WebSocket（不经过 Gateway）

```
WebSocket 客户端

  ▼
AuthHandshakeInterceptor (mall-message)
```

## 三、信任模型

### 3.1 信任原则

| 原则 | 说明 |
|------|------|
| **JWT 为最终信任源** | 无论 `X-User-*` 头写什么，都以 JWT claims 为准 |
| **Header 非信任源** | `X-User-Id` / `X-User-Name` / `X-Roles` 仅作辅助比对 |
| **拒绝裸 Header** | 有 X-User-* 头但无 JWT → 直接 401 |
| **双校验** | Header 声明与 JWT claims 不一致 → 直接 401 |

### 3.2 攻击面分析

| 场景 | 风险 | 防护机制 |
|------|------|---------|
| 外部客户端伪造 X-User-* 头 | ❌ 不可能 | Gateway AuthFilter 用 JWT claims **覆写**所有头 |
| 内网直调后端 + 伪造 X-User-* 头 | ⚠️ 被拦截 | AuthApiInterceptor 要求 JWT + Header 双校验 |
| 内网直调后端 + 有效 JWT | ✅ 正常 | 合法调用，按 JWT 身份授权 |
| 内网直调后端 + 无身份 | ✅ 放行 | 公开接口走 Spring Security permitAll |
| JWT 泄露 | ⚠️ 需要 | Redis 黑名单（仅 mall-admin）+ 定期轮换密钥 |

### 3.3 信任传递链

```
Gateway 验签
  ↓ 信任传递（非信任 → 验证后覆盖）
AuthApiInterceptor 双重校验
  ↓ JWT claims 为最终信任源
SecurityContext 设置
  ↓
Spring Security 授权决策
  ↓
业务逻辑执行
```

## 五、内部接口（`/v1/internal/`）

### 用途

Feign 服务间调用专用路径，不走 Gateway。

### 豁免

| 组件 | 豁免内容 |
|------|---------|
| `SpringSecurityConfig`（mall-admin） | `.requestMatchers("/v1/internal/**").permitAll()` |
| `GlobalApiResultHandler` | 跳过 `/v1/internal/` 路径，不包裹 `ApiResult` |

### 安全说明

虽然 `AuthApiInterceptor` 依然处理 `/v1/internal/` 请求，但 FeignAuthInterceptor 透传的 Authorization 头会被正确解析。如果 Feign 调用方未登录（无 JWT），则后端收到的是"无身份"请求 → 拦截器放行 → Spring Security 的 permitAll 也放行。因此内部接口本身**不依赖用户身份**（例如根据 ID 查数据、扣库存等），而是依赖**网络隔离**和**调用方控制**做安全。

## 七、关键设计决策

| 决策 | 理由 |
|------|------|
| Gateway 保留 Authorization 头 | 后端服务需要独立验签，不依赖 X-User-* 头 |
| AuthApiInterceptor 不信任 Header | 防止内网横向移动时伪造身份 |
| FeignAuthInterceptor 透传 Authorization | Feign 调用带上原始令牌，后端独立验证 |
| JwtTokenFilter 仅限 mall-admin | 只有 admin 需要踢人下线（C 端不需） |
| 不使用 `@NoLogin` 注解 | 统一由 Gateway 白名单控制，不分散到各服务 |
| starter 不走 `scanBasePackages` | 通过 `AutoConfiguration.imports` 生效，不受服务级扫描范围限制 |
