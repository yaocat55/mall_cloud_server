## 一、渠道 CSV 字段 vs recon_temp 字段对照

### 支付宝业务账单（bill_type=trade）

CSV 字段（23 列）与 `recon_temp` 映射：

| CSV 字段 | recon_temp 字段 | 说明 |
|------|------|------|
| 支付宝交易号 | `channel_trade_no` | 渠道侧唯一交易号 |
| 商户订单号 | `trade_no` | = `merchant_order_no`，**对账匹配键** |
| 业务类型 | `trade_type` | "交易支付" → `PAY`，"退款" → `REFUND` |
| 商品名称 | — | 不入库，仅排查用 |
| 完成时间 | `trade_time` | |
| 订单金额（元） | `amount` | **需 ×100 转分** |
| 商家实收（元） | `income` | **需 ×100 转分** |
| 服务费（元） | `fee` | **需 ×100 转分** |
| 退款批次号/请求号 | `refund_no` | 退款记录行才有，支付行为空 |
| 对方账户 | `payer_account` | |
| 其他字段（门店、操作员等） | `ext_json` | 原样保留备查 |

**支付宝对账单编码：** GBK，压缩格式 `.csv.zip`。

**支付宝对应接口：** `alipay.data.dataservice.bill.downloadurl.query`（`bill_type=trade`），链接 30 秒有效。

### 微信交易账单（bill_type=ALL）

CSV 字段（29 列）与 `recon_temp` 映射：

| CSV 字段 | recon_temp 字段 | 说明 |
|------|------|------|
| 微信订单号 | `channel_trade_no` | 渠道侧唯一交易号 |
| 商户订单号 | `trade_no` | = `merchant_order_no`，**对账匹配键** |
| 交易状态 | `trade_status` | `SUCCESS` → 支付、`REFUND` → 退款 |
| 交易时间 | `trade_time` | |
| 应结订单金额（元） | `amount` | **需 ×100 转分**，退款行为 0 |
| 退款金额（元） | — | 退款行才有，作为 amount 参考 |
| 手续费（元） | `fee` | **需 ×100 转分** |
| 微信退款单号 | `refund_no` | 退款行才有 |
| 商户退款单号 | — | 入 ext_json |
| 用户标识 | `payer_account` | |
| 其他字段 | `ext_json` | 原样保留备查 |

**微信对账单编码：** UTF-8，纯 `.csv` 文件。

**微信对应接口：** `GET /v3/bill/tradebill?bill_date=xxx&bill_type=ALL`，链接 5 分钟有效。

### ⚠️ 两渠道关键差异

| | 支付宝 | 微信 |
|------|------|------|
| 编码 | GBK | UTF-8 |
| 压缩 | `.csv.zip`（需解压） | 纯 `.csv` |
| `income` | 直接有"商家实收"列 | **没有**，需 `amount - fee` 计算 |
| 区分支付/退款行 | "业务类型"列 | "交易状态"列 |
| 汇总行 | CSV 末尾有汇总行 | CSV 末尾有汇总行（`\`` 开头）|
| 下载链接时效 | 30 秒 | 5 分钟 |
| 金额单位 | 元 | 元 |
| 退款行手续费 | 不适用 | **为负数**（平台退回手续费） |

> **共同点**：两渠道 CSV 字段均以英文逗号分隔，每字段前有反引号（\`）字符（防 Excel 科学计数法），解析时需去除。均以"商户订单号"作为对账匹配键。

## 二、对账算法设计

### 总额校验（第一道闸，O(1) 判定）

```sql
-- 渠道侧：当天所有交易的净额汇总
SELECT COUNT(*), SUM(income) FROM recon_temp WHERE batch_no = ?

-- 平台侧：当天所有支付单的净额（支付金额 - 退款金额）
SELECT COUNT(*), SUM(pay_amount) - SUM(refund_amount)
FROM pay_order
WHERE channel_code = ? AND success_time >= ? AND success_time < ?
  AND pay_status = 20 AND is_del = 0
```

| 结果 | 含义 | 处置 |
|------|------|------|
| 相等 | **对平** ✅ | 关闭批次，终态 |
| 渠道多 / 平台少 | **长款**（我方少记收款） 🔴 | 进入逐笔对比 |
| 渠道少 / 平台多 | **短款**（我方多记收款） ⚠️ | 进入逐笔对比 |

> 绝大部分情况下总额校验即可对平，无需进入逐笔对比。

### 逐笔对比（第二道闸，仅在总额不等时进入）

**核心思路：双批查询 + 内存 HashMap 撮合，不 JOIN。**

为什么不 JOIN：日均对账笔数千级，JOIN 是浪费；且未来分库分表时联表不可行——HashMap 撮合在应用层做，不受分库影响。

```
① 渠道侧批量查询：
   SELECT trade_no, amount, income, fee, trade_type, channel_trade_no
   FROM recon_temp WHERE batch_no = ?
   → 加载到 Map<String, ReconTempEntity> channelMap

② 平台侧批量查询：
   SELECT merchant_order_no, pay_amount, pay_order_no, success_time
   FROM pay_order WHERE channel_code = ? AND success_time IN [对账日窗口]
   → 加载到 Map<String, PayOrderEntity> platformMap

③ 渠道遍历（找渠道有、平台无的）：
   for (channel每一笔) {
       platformMatch = platformMap.get(trade_no)
       if (命中) → 对比金额 → 一致跳过 / 不一致写 AMOUNT_MISMATCH
       else → 写 ONLY_CHANNEL（渠道有单、我方无 = 回调丢失）
   }

④ 平台遍历（找平台有、渠道无的）：
   for (平台每一笔) {
       if (!channelMap.containsKey(merchant_order_no))
           → 写 ONLY_PLATFORM（我方有单、渠道无 = 虚记）
   }
```

逐笔差异写入 `recon_result`，`diff_type` 分 7 种（见 `docs/37` 3.8 节）。

### 时间对齐

渠道对账单的"交易时间"和我方 `success_time` 是两个时钟，差几秒到几分钟正常（回调延迟）：

- 平台侧查单用 `success_time` + 缓冲窗口（`[trade_date 00:00, trade_date+1 06:00)`）
- 逐笔匹配只认 `merchant_order_no` 相等，不对齐时间

## 三、对账流水线

```
@Scheduled cron="0 30 10 * * ?"  （次日 10:30 触发，两家渠道次日 10 点后账单就绪）
  │
  ├─ Step 1: 遍历启用渠道（ALIPAY / WECHAT_PAY）
  │    └─ 查 recon_batch 是否已有当日批次 → 有则跳过（幂等）
  │
  ├─ Step 2: channelStrategy.downloadBill(tradeDate) → byte[]
  │    └─ 调渠道 API 获取下载链接 → HTTP 下载 → 存 MinIO
  │
  ├─ Step 3: channelStrategy.parseBill(content) → List<BillRow>
  │    └─ BillCsvParser 解析 CSV → BillRow（渠道无关中间结构）
  │
  ├─ Step 4: 批量 INSERT INTO recon_temp（按 batch_no 隔离）
  │
  ├─ Step 5: 总额校验 → 对平？结束：进入 Step 6
  │
  └─ Step 6: 逐笔对比（HashMap 内存撮合）
       └─ 差异写 recon_result
```

## 四、BillRow（渠道无关中间结构）

设计目的：支付宝 23 列、微信 29 列，解析后归一化为统一的 `BillRow`，对账引擎只认 `BillRow`。

> 已有字段（`BillRow.java`）：`tradeNo, channelTradeNo, refundNo, tradeTime, tradeType, amount, fee, income, tradeStatus, payerAccount, extJson`

无需修改，上面对照表已经验证了每个字段都能从两渠道 CSV 中获取。
