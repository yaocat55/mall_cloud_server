# 统一支付服务设计方案


> 📌 **归档说明：** `mall-admin-bff` 已于 2026-08-03 整体拆除，admin 前端直连各微服务（见 `40-adminBFF拆除方案.md`）。本文档描述的 admin-bff 相关内容已过时，仅作历史演进记录；mobile-bff 部分仍有效。
## 背景

当前 `mall-pay` 模块是**模拟支付**，存在以下问题：

- 只有一个 `mockPay` 接口，收到前端传来的订单号后，直接改订单状态为已支付，无任何真实支付行为
- 没有自己的数据库，唯一的外部数据源是 mall-order 的 Feign 查询
- `PayStatusEnum` 只有 4 个状态（待支付/已支付/已退款/失败），无法表达真实支付链路中的中间态（支付中、已关闭、退款中、部分退款等）
- `PayService.mockPay` 直接持有 `orderFeignClient`，依赖方向是 mall-pay → mall-order；而 mall-order 又通过 `PayFeignClient` 调用 mall-pay，**已存在循环依赖隐患**
- 渠道集成只有 Alipay 一种雏形，无法扩展微信支付、微信小程序支付及未来其他国内支付渠道

目标：将 mall-pay 改造为**统一支付服务**——拥有自己的数据库，聚合支付宝/微信支付/微信小程序支付等移动端支付渠道，设计可扩展的多渠道架构，并配套一套**每日对账系统**（拉取渠道对账单 → 解析 → 大批量入临时表 → 与本地支付订单对比 → 大小款计算 → 差异结论 → 兜底措施），使其日后可作为独立支付服务接入其他项目。

### 1.2 关键决策（2026-08 已确认）

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 数据库 | 独立 `cloud_mall_pay`，单库不分片 | 支付数据量适中，不需要分库分表；ShardingSphere 留给订单 |
| 金额单位 | **分（bigint）**（已确认） | 所有国内支付 SDK 金额均以分为单位；对账需要精确加减避免浮点误差；与 `decimal` 相比省空间、无精度问题 |
| ID 生成 | 雪花 ID（common-workid） | 与项目其他模块一致；支付单号、退款单号、对账批次号均由服务生成 |
| 并发控制 | 乐观锁 `version` | 状态流转（回调/退款/对账）用 `UPDATE ... SET status=?, version=version+1 WHERE id=? AND version=?` 防止重复处理 |
| 审计字段 | `create_user_id/create_user_name/create_time/update_user_id/update_user_name/update_time` | 与项目 `FillUserUtil` / `BaseEntity` 规范一致 |
| 渠道扩展 | 策略模式 `PayChannelStrategy` | 新增渠道 = 新增一个策略实现 + 一张渠道配置，不改核心流程 |
| 业务通知 | **统一 MQ 异步通知**（已确认） | 支付/退款结果通过 RocketMQ 异步通知业务方，pay 服务不再依赖 order-client，消除循环依赖、支持多业务方 |
| 回调地址 | **渠道回调直连 pay 服务**（已确认） | 渠道 notify_url 直接打到 mall-pay，网关放行回调路径；不走 BFF |
| 对账存储 | **MinIO 对象存储**（已确认，预留扩展） | 对账单原件存 MinIO；接口按对象存储抽象，后期可扩展其他存储，当前先调用 MinIO 接口 |
| 对账调度 | **`@Scheduled` 内置定时**（已确认，后期迁 xxl-job） | 项目现无统一调度中心，先内置定时；后期重构时引入 xxl-job |
| 商户号 | **先统一商户号**（已确认） | 微信支付（App）与微信小程序支付先共用商户号；后期需要分开计算时再拆分渠道配置 |
| 业务接入 | **独立业务渠道接入表**（`pay_biz_config`） | 每个接入业务方（`biz_type`）注册一行，含名称/回调地址/密钥；见 2.5 节 |
| **无联表查询** | **支付库表之间不设外键、不做 JOIN**；**宁可代码层/单表设计冗余字段，也尽可能避免联表查询**——跨表信息靠冗余字段 + 唯一索引（如 `merchant_order_no`）+ 应用层二次查询完成 | 单表查询是后续分库分表的前提：一旦跨表 JOIN，扩容时分片键无法路由，必须全分片广播扫描，必然出错或退化。对账逐笔对比也因此设计为**双批查询内存撮合**（见 6.2 Step 4） |

**MOCK 模拟渠道（开发/测试联调必需）：**

> **背景**：dev/test 环境没有真实商户号，支付全流程（下单/回调/退款/对账）无法联调；且支付宝沙箱下载的对账单为空。必须保留一个 `MOCK` 渠道策略供开发/测试环境使用。
>
> - `channel_code = MOCK`，实现 `PayChannelStrategy` 全接口：`prepay` 直接返回预设的成功参数、`refund` 直接成功、`downloadBill` 返回内存构造的账单
- **仅 dev/test 环境启用**（prod 配置禁用），通过渠道配置 `status=0` 或环境配置开关控制
- 保证开发、测试、CI 流水线在无真实商户号时仍能完整跑通支付与对账链路
- 对接真实渠道时，MOCK 与真实渠道共用同一套 `PayChannelStrategy` 调用方逻辑，无感知切换

统一接口 `PayChannelStrategy`，各渠道实现，**本次设计先行约定接口，具体实现分阶段落地**：

```java
public interface PayChannelStrategy {
    /** 渠道编码：ALIPAY / WECHAT_PAY / WECHAT_MINI */
    String channelCode();

    /** 创建支付单，返回拉起支付所需参数（调起 SDK 的 json/字符串） */
    PayPrepayResult prepay(PayOrder payOrder, PayChannelConfig config);

    /** 主动查询订单状态（兜底轮询用） */
    PayQueryResult query(String merchantOrderNo, PayChannelConfig config);

    /** 关闭未支付订单 */
    boolean close(String merchantOrderNo, PayChannelConfig config);

    /** 申请退款 */
    RefundResult refund(PayRefund refund, PayChannelConfig config);

    /** 查询退款结果 */
    RefundQueryResult queryRefund(String refundNo, PayChannelConfig config);

    /** 回调报文验签 */
    boolean verifyNotify(Map<String, String> params, String rawBody, PayChannelConfig config);

    /** 解析回调报文为统一对象 */
    PayNotifyMessage parseNotify(String rawBody, PayChannelConfig config);

    /** 下载对账单，返回文件内容 */
    byte[] downloadBill(LocalDate tradeDate, PayChannelConfig config);

    /** 解析对账单 → 统一账单行结构 */
    List<BillRow> parseBill(byte[] content);
}
```

## 二、业务依赖字段设计（通用性核心）

支付服务要作为**可复用的统一支付服务**接入多个业务系统（商城订单、会员充值、知识付费、外卖点单……），就不能被任何特定业务的字段绑架。设计原则是：**只保留所有业务都具备的「基本面」字段，业务专属字段一律不落支付库**。

### 2.1 原则：支付库不存业务字段

- 支付服务**不感知**业务方内部结构：不管业务方是订单、充值单还是订阅单，对支付服务而言只有一个「业务单号」
- 业务专属信息（商品明细、收货地址、优惠明细、发票抬头等）**留在业务方自己的库里**，支付服务只在回调/查询时按 `biz_order_no` 反查业务单号，不复制业务数据
- 这样做的收益：**接入新业务方 = 零表结构改动**，只要业务方能提供下表的字段即可

### 2.2 支付服务对业务方的最少依赖字段

| # | 字段 | 对应商城订单字段 | 说明 | 是否必须 |
|---|------|----------------|------|:---:|
| 1 | `biz_order_no` | `trade.code`（订单编码） | 业务方订单号，支付服务的"外键" | ✅ |
| 2 | `biz_type` | 固定为 `MALL_ORDER` | 区分不同业务方/业务类型，各业务方分配唯一编码 | ✅ |
| 3 | `user_id` | `trade.user_id` | 发起支付的用户 ID | ✅ |
| 4 | `subject` | `orderItemList[].productName` 拼接 | 商品描述，收银台展示 | ⚠️ 渠道要求 |
| 5 | `total_amount` | `trade.total_amount`（总金额） | 应付金额，渠道下单必传 | ✅ |
| 6 | `channel_code` | 由前端选渠道传入 | 支付渠道：ALIPAY / WECHAT_PAY / WECHAT_MINI | ✅ |
| 7 | `open_id` | 商城无（微信体系用户才有） | 微信小程序支付必填；其他渠道可空 | ⚠️ 按渠道 |
| 8 | `client_ip` | 由调用方透传 | 部分渠道风控要求 | ⚠️ 可选 |
| 9 | `remark` | `trade.remark` | 备注 | ⚠️ 可选 |

**必须字段只有 6 个**：`biz_order_no`、`biz_type`、`user_id`、`total_amount`、`channel_code`，外加渠道可能要求的 `subject`。其余全部可选。

> 📌 金额口径：商城订单 `total_amount`（总金额）与 `pay_amount`（付款金额）可能不同（券后实付）。支付服务以**用户实际要付的钱**即 `pay_amount` 作为 `total_amount` 提交渠道；本地 `pay_amount` 字段仍以渠道回传的实付为准。如果业务方无法提供 `subject`，支付服务可用 `biz_order_no` 兜底生成描述，保证渠道下单不失败。

### 2.3 与现有商城订单的字段映射（对照）

接入商城订单（mall-order）时，一次典型的支付创建请求如下，可验证依赖面是否够窄：

```json
{
  "bizOrderNo": "TC202408010001",
  "bizType": "MALL_ORDER",
  "channelCode": "WECHAT_MINI",
  "userId": 10086,
  "subject": "商城订单 TC202408010001（2 件商品）",
  "totalAmount": 39900,
  "openId": "oXk9zTvRqyLh3mSd5nBf7GjA8wPq",
  "clientIp": "10.0.0.1",
  "remark": ""
}
```

对照 `OrderDTO`：`bizOrderNo` ← `trade.code`，`userId` ← `trade.user_id`，`totalAmount` ← `trade.pay_amount`（实付），`subject` ← 由 `orderItemList[].productName` 拼接。**没有依赖**订单明细、收货地址、优惠明细、物流等任何商城专属字段。

### 2.4 未来业务方接入的扩展点

| 场景 | 方案 |
|------|------|
| 新增业务方（如会员充值） | 分配新 `biz_type` 编码，支付表**零改动** |
| 业务方有自定义展示信息 | 已预留 `subject`/`body`/`remark` 三个通用展示字段 |
| 业务方需关联凭证/订单图片 | 走 `biz_order_no` 反查，不落支付库 |
| 渠道特有参数（如支付宝 `passback_params`） | 走渠道 `ext_json`，不污染通用结构 |
| 对账按业务方分类 | `biz_type` 天然支持对账结果按业务方维度汇总 |

> ⚠️ 新手提示：`subject`/`body` 有长度限制（支付宝 256 字节、微信 128 字节），字段设计为 `varchar(128)`/`varchar(512)` 已经覆盖；拼接多商品描述时注意截断。**`subject` 不强求业务方提供**——它更多是支付用户自己的备注语义，业务方缺失时用 `biz_order_no` 兜底生成，保证渠道下单不失败（已确认）。

### 2.5 业务渠道接入表（pay_biz_config）

每个接入的业务方（`biz_type`）在支付服务中注册一行，作为多业务方接入的**配置底座**（已确认，独立表维护）。

```sql
CREATE TABLE `cloud_mall_pay`.`pay_biz_config` (
    `id`                 bigint       NOT NULL PRIMARY KEY  COMMENT '主键，雪花ID',
    `biz_type`           varchar(32)  NOT NULL              COMMENT '业务类型编码（唯一，如 MALL_ORDER）',
    `biz_name`           varchar(64)  NOT NULL              COMMENT '业务方名称（如 商城订单）',
    `notify_mq_topic`    varchar(64)  NOT NULL              COMMENT '业务方接收支付结果通知的 MQ Topic',
    `notify_mq_tag`      varchar(64)          DEFAULT NULL   COMMENT 'MQ Tag（可选，用于过滤）',
    `sign_key`           text                DEFAULT NULL   COMMENT '业务方回调验签密钥（AES 加密存储，预留）',
    `status`             tinyint      NOT NULL DEFAULT 1    COMMENT '状态：1启用 0禁用',
    `remark`             varchar(255)         DEFAULT NULL   COMMENT '备注',
    `create_user_id`     bigint       NOT NULL              COMMENT '创建人ID',
    `create_user_name`   varchar(64)  NOT NULL              COMMENT '创建人姓名',
    `create_time`        datetime(3)  NOT NULL              COMMENT '创建时间',
    `update_user_id`     bigint       NOT NULL              COMMENT '更新人ID',
    `update_user_name`   varchar(64)  NOT NULL              COMMENT '更新人姓名',
    `update_time`        datetime(3)  NOT NULL              COMMENT '更新时间',
    `is_del`             tinyint      NOT NULL DEFAULT 0    COMMENT '逻辑删除：0否 1是',
    UNIQUE KEY `uk_biz_type` (`biz_type`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='业务渠道接入表';
```

**设计要点：**
- **新增业务方 = 插一行**：分配唯一 `biz_type` + 通知 MQ Topic，支付表**零改动**，无需改代码
- 通知方式为 **MQ 异步**（已确认），`notify_mq_topic` 记录每个业务方各自消费的 Topic
- `sign_key` 预留业务方回调验签，AES 加密存储
- 对账按 `biz_type` 天然支持按业务方维度汇总

## 三、数据库设计（cloud_mall_pay）

共 **8 张表**：业务侧 5 张（pay_order / pay_notify_log / pay_refund / pay_channel_config / pay_biz_config），对账侧 3 张（recon_batch / recon_temp / recon_result）。

### 3.1 pay_order 支付订单表（核心）

一笔业务订单对应**一条支付订单**（支持一单多支付单场景：支付单过期后重新发起，业务订单不变）。

```sql
CREATE DATABASE IF NOT EXISTS `cloud_mall_pay` DEFAULT CHARSET utf8mb4;

CREATE TABLE `cloud_mall_pay`.`pay_order` (
    `id`                 bigint       NOT NULL              COMMENT '主键，雪花ID',
    `pay_order_no`       varchar(32)  NOT NULL              COMMENT '支付订单号（对外交易号，雪花ID字符串）',
    `biz_order_no`       varchar(64)  NOT NULL              COMMENT '业务方订单号（如商城 tradeCode）',
    `biz_type`           varchar(32)  NOT NULL              COMMENT '业务类型：MALL_ORDER 商城订单 / OTHER 其他',
    `channel_code`       varchar(16)  NOT NULL              COMMENT '支付渠道：ALIPAY / WECHAT_PAY / WECHAT_MINI / MOCK（模拟渠道，仅 dev/test 启用）',
    `merchant_order_no`  varchar(64)  NOT NULL              COMMENT '渠道商户订单号（本地唯一，渠道侧可回溯）',
    `channel_trade_no`   varchar(64)          DEFAULT NULL   COMMENT '渠道交易号（回调成功后回填）',
```

**字段设计要点：**

- **`merchant_order_no` 与 `pay_order_no` 双号**：`pay_order_no` 是支付服务对外暴露的业务号；`merchant_order_no` 是提交给渠道的商户订单号（各渠道对商户订单号格式有约束，如微信限制 6-32 位字母数字）。两者都唯一，渠道对账单/回调里带的是 `merchant_order_no`，用于回溯 `pay_order_no`。
- **`biz_order_no` + `biz_type`**：绑定业务订单，用于可追溯。对账时如果渠道侧出现的订单本地没有，用 `biz_order_no` 反查业务方订单确认是否真实发生交易。
- **金额分三份**：`total_amount`（应付）、`pay_amount`（实付，渠道优惠可能导致实付≠应付）、`refund_amount`（已退累计）。对账"大小款"对比以 `pay_amount` 为准。
- **`pay_status` / `refund_status` 拆开**：一个订单可以"已支付 + 部分退款"，单一状态字段表达不了，所以拆两个维度。
- **`notify_count` / `notify_time` / `biz_notify_status`**：渠道回调幂等、业务方通知补偿的支撑字段。
- **对账时间索引**：`idx_channel_success_time (channel_code, success_time)` 专为对账窗口检索设计——对账按「渠道 × 时间窗」批量拉取平台侧记录，联合索引先等值走渠道、再范围走时间，一次索引定位。`success_time` 只在支付/退款**成功落库时写入**，是平台侧唯一可靠的时间锚点（见 6.2 Step 3 时间对齐说明）。

### 3.5 pay_biz_config 业务渠道接入表

每个接入的业务方（`biz_type`）在支付服务中注册一行，作为多业务方接入的**配置底座**（已确认，独立表维护）。建表 SQL 见 2.5 节，此处为表结构位置说明。

**设计要点：**
- **新增业务方 = 插一行**：分配唯一 `biz_type` + 通知 MQ Topic，支付表**零改动**，无需改代码
- 通知方式为 **MQ 异步**（已确认），`notify_mq_topic` 记录每个业务方各自消费的 Topic

### 3.7 recon_temp 对账临时表（核心）

**对账临时表的设计目标：** 渠道对账单（excel/csv）解析后**大批量插入**，然后与本地 `pay_order` 表做关联对比。设计上要满足：

1. **可批量灌入**：字段扁平、宽表，支持 `LOAD DATA` 或批量 `INSERT`
2. **多渠道兼容**：支付宝/微信/小程序对账单字段各异，用「通用字段 + ext_json 扩展列」吸收差异
3. **按批次隔离**：`batch_no` 区分不同批次数据，同表复用，无需物理建表
4. **保留期可清理**：对账完成保留 N 天便于排查，之后批量删除

```sql
CREATE TABLE `cloud_mall_pay`.`recon_temp` (
    `id`                bigint       NOT NULL AUTO_INCREMENT  COMMENT '自增主键（临时表专用，非雪花）',
    `batch_no`          varchar(32)  NOT NULL                 COMMENT '对账批次号',
    `line_no`           int          NOT NULL                 COMMENT '文件行号',
    `trade_no`          varchar(64)  NOT NULL                 COMMENT '渠道商户订单号（= merchant_order_no）',
    `channel_trade_no`  varchar(64)           DEFAULT NULL    COMMENT '渠道交易流水号',
    `refund_no`         varchar(64)           DEFAULT NULL    COMMENT '渠道退款单号（退款记录行才有）',
    `trade_time`        datetime     NOT NULL                 COMMENT '交易时间',
    `trade_type`        varchar(16)  NOT NULL                 COMMENT '交易类型：PAY 支付 / REFUND 退款',
    `amount`            bigint       NOT NULL                 COMMENT '交易金额（分，正数）',
    `fee`               bigint       NOT NULL DEFAULT 0       COMMENT '手续费（分）',
    `income`            bigint       NOT NULL DEFAULT 0       COMMENT '净入账金额（分，amount - fee，可正可负）',
    `trade_status`      varchar(16)           DEFAULT NULL    COMMENT '渠道交易状态：SUCCESS/REFUND/CLOSED',
    `payer_account`     varchar(64)           DEFAULT NULL    COMMENT '付款方账号',
    `ext_json`          json                  DEFAULT NULL    COMMENT '渠道特有字段（原样保留）',
    `create_time`       datetime(3)  NOT NULL                 COMMENT '入库时间',
    PRIMARY KEY (`id`),
    KEY `idx_batch_no` (`batch_no`),
    KEY `idx_batch_trade_no` (`batch_no`, `trade_no`),
    KEY `idx_batch_trade_time` (`batch_no`, `trade_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='对账临时表（按批次批量插入，对账完成保留N天后清理）';
```

**「大小款对比」的核心依托：** 对账时用 `SUM(income)` 得到**渠道侧净额**，用 `SUM(pay_amount) - SUM(refund_amount)` 得到**平台侧净额**，两者相减即长款/短款总额。逐笔对比不 JOIN——**双批查询 + 内存撮合**，按 `trade_no = merchant_order_no` 在应用层匹配（见 6.2 Step 4）。

## 四、支付状态机

### 4.1 支付状态 pay_status

```
                    ┌─────────┐
                    │ 10 待支付 │◄──────────────┐ 超时/取消后重发支付单
                    └────┬────┘                │
          ┌──────────────┼──────────────┐      │
          │回调成功        │主动查单成功     │      │
          ▼              ▼              ▼      │
    ┌─────────┐   ┌─────────┐    ┌─────────┐  │
    │ 20 已支付 │   │ 30 已关闭 │    │ 40 支付失败│ │
    └────┬────┘   └─────────┘    └─────────┘  │
         │ 超时未付/用户取消                      │
         ▼                                     │
    重新发起支付（新建 pay_order）────────────────┘
```

- 支付状态只关心「收钱」；收完钱之后的退款，走 `refund_status` 维度，**不回退 pay_status**
- **`待支付`（10）与 `支付中`（20）已合并为单一待支付态**——从创建支付单到用户完成支付操作，统一为 `10 待支付`；到 `20 已支付` 由**渠道回调或主动查单**确认，不做本地乐观判定
- `20 已支付` 是终态之一；`30 已关闭`（超时/取消）可重新发起新的支付单（业务订单不变）

**PayStatusEnum 最终定义（对应表 `pay_order.pay_status`）：**

```java
package cn.net.mall.pay.enums;

import lombok.AllArgsConstructor;
import lombok.Getter;

/**
 * 支付状态枚举（对应 pay_order.pay_status）
 * 状态只关心「收钱」；收完钱之后的退款走 refund_status 维度，不回退 pay_status
 * 待支付/支付中已合并为单一待支付态（10）
 */
@AllArgsConstructor
@Getter
public enum PayStatusEnum {

    /** 10 待支付：支付单已创建（含已调起渠道、用户支付操作进行中）；超时/取消可重发新支付单 */
    WAIT_PAY(10, "待支付"),

    /** 20 已支付：渠道回调或主动查单确认成功，终态 */
    PAYMENT(20, "已支付"),

    /** 30 已关闭：超时未付/用户主动取消，可重新发起支付单 */
    CLOSED(30, "已关闭"),

    /** 40 支付失败：渠道明确返回失败（余额不足/风控拦截/交易关闭） */
    FAILURE(40, "支付失败");

    private final Integer value;
    private final String desc;
}
```

**各状态可能的场景（备注）：**

| 状态 | value | 进入场景 | 可流转去向 |
|------|:---:|---------|-----------|
| 待支付 | 10 | 创建支付单成功（含调起渠道拿到 prepay、用户拉起支付但未回调）、超时关单后重发新支付单 | 已支付 / 已关闭 / 支付失败 |
| 已支付 | 20 | 渠道回调验签成功、主动查单确认成功 | 终态（退款走 refund_status） |
| 已关闭 | 30 | 超时未付自动关单、用户主动取消、渠道明确拒绝 | 重新发起新支付单 |
| 支付失败 | 40 | 渠道明确返回失败（余额不足 / 风控拦截 / 交易关闭） | 可重新发起新支付单 |

> 状态语义对照：原 `PayStatusEnum`（WAIT_PAY/PAYMENT/REFUND/FAILURE）把"已退款"当支付状态，无法表达"已支付 + 部分退款"；新设计将退款剥离到 `refund_status` 维度，pay_status 只表达收钱进度。`支付中`/`待支付` 已合并为单一待支付态（10），不区分"是否已调起渠道"。

#### 典型支付场景 → 双状态流转（业务订单 × 支付单）

> 业务订单状态见 `mall-order-client` 的 `OrderStatusEnum`；支付单状态即本表 `pay_status`。两张表解耦：**业务订单管"交易履约"（已下单→已支付→已发货…），支付单只管"收钱"（待支付→已支付/已关闭/支付失败）**。

| 用户场景 | 业务订单状态 | 支付单状态（pay_status） | 说明 |
|---------|:---:|:---:|------|
| 下单成功 | 已下单(1) | 待支付(10) | 业务订单创建，支付单待支付 |
| 支付成功 | 已支付(2) | 已支付(20) | 渠道回调/主动查单确认，支付单终态 |
| 中途打断支付（返回手势/杀进程） | 已下单(1) | 待支付(10) | 用户未完成支付，可重新拉起/继续支付 |
| 用户主动取消订单 / 业务订单超时 | 已取消(5) | 已关闭(30) | 用户主动放弃支付 |
| 支付单超时（expire_time 到期） | 已下单(1) | 已关闭(30) | 超时未付自动关单，可重发新支付单 |
| **资金不足 / 风控拦截 / 交易关闭** | 已下单(1) | **支付失败(40)** | **渠道明确拒绝**，与"已关闭"区分：已关闭=用户主动放弃，支付失败=被动失败 |

> ⚠️ **关键区分：`已关闭(30)` vs `支付失败(40)`**
> - `已关闭(30)`：**用户主动行为**（取消/返回）或 **超时**——钱没动，是"不付了"
> - `支付失败(40)`：**渠道明确拒绝**（余额不足/风控/交易关闭）——用户**尝试付但失败了**
> 两者对账、风控、前端提示（"已取消" vs "支付失败，请重试"）处理完全不同，不可混用。资金不足必须标 `40 支付失败`，业务订单保持已下单(1) 可重新发起。

### 4.2 退款状态 refund_status（支付单维度）

```
            0 无退款
            │ 发起第一笔退款
            ▼
    ┌─────────────────┐   渠道退款成功(部分)   ┌──────────────┐
    │ 1 退款中         │ ────────────────────►│ 2 部分退款     │
    └────────┬────────┘                       └──────────────┘
             │ 渠道退款成功(累计=pay_amount)
             ▼
    ┌──────────────┐
    │ 3 全额退款    │
    └──────────────┘
    退款失败 → 4 退款失败（可重试，从 pay_refund.refund_status 流转）
```

### 4.3 退款单状态（pay_refund 维度）

```
0 待处理 → 1 处理中（已提交渠道） → 2 退款成功
                          ↘ 3 退款失败（可重新发起退款单）
审核：0 无需审核 / 1 待审核 / 2 审核通过 / 3 审核拒绝
```

**退款审核触发条件（已确认）：**
- **默认优先自动退款**：正常退款请求直接提交渠道，无需人工介入
- **进入人工审核（`audit_status=1 待审核`）的触发条件**：退款请求中携带的**商品订单（`biz_order_no`）或退款申请人（`user_id`）在支付订单库 `pay_order` 中查询不到**——即查不到这笔支付单（可能是伪造退款、订单不存在、或数据异常）
- 审核通过（`audit_status=2`）后才提交渠道退款；审核拒绝（`audit_status=3`）则退款终止并通知业务方

### 4.4 状态流转的并发控制

所有状态变更统一走乐观锁：

```sql
UPDATE pay_order
   SET pay_status = #{target}, version = version + 1, update_time = NOW()
 WHERE id = #{id} AND version = #{expectVersion}
   AND pay_status IN (#{fromStatuses})   -- 前置状态约束
```

回调处理时 `fromStatuses` 限定 `(10)` → 回调幂等，重复回调命中 `20`（已支付）直接跳过。退款累计额更新同样带 `version` 和「已退金额+本次 ≤ pay_amount」约束。

## 五、核心流程

### 5.1 创建支付单（mall-order → mall-pay）

```
mall-order 下单成功（业务订单=WAIT_PAY）
    │
    ▼
POST /v1/pay/create  { bizOrderNo, bizType, channelCode, subject, totalAmount, userId, openId? }
    │
    ▼
1. 校验：渠道已启用、金额>0、同 bizOrderNo 未存在进行中支付单
2. 生成 pay_order（雪花ID 主键、pay_order_no、merchant_order_no）
3. 渠道 prepay() → 返回拉起支付参数（支付宝参数串 / 微信预支付单 sign）
4. 返回 { payOrderNo, prepayParams }
    │
    ▼
前端收银台调起支付
```

**创建幂等（防并发/重试重复建单）**：
- 业务方网络超时重试、前端重复点击时，同一 `biz_order_no` 可能**并发**发起多次创建
- 应用层先查「同 `biz_type + biz_order_no` 存在进行中支付单」→ 存在直接返回已有支付单；但并发下仍可能同时插入
- **兜底靠 `uk_merchant_order_no` 唯一索引**：插入冲突时捕获唯一键异常，反查已存在的支付单返回（对调用方表现为幂等，不报错）
- `merchant_order_no` 由**支付服务在创建时生成**（雪花 ID 派生），不是业务方传入，保证全局唯一且格式满足渠道约束

### 5.2 支付回调处理（渠道 → mall-pay → mall-order）

```
渠道异步通知
    │
    ▼
1. 先落 pay_notify_log（原始报文不丢）
2. 验签（具体算法见 `docs/39` 第二章「加密与签名机制」）：
    支付宝：RSA2（SHA256withRSA）用支付宝公钥验签
    微信：SHA256-RSA2048 用微信平台证书验签 + AES-256-GCM 解密（APIv3 密钥）
    成功 → 继续
    失败 → 返回失败给渠道，渠道会重试
3. 防重放（安全加固）：校验渠道回调中的 timestamp 在合理窗口内（如 5 分钟内），超窗丢弃；校验 nonce 是否已处理过（Redis 短 TTL 去重）——防止恶意重放历史报文
4. 来源校验：可配置渠道回调来源 IP 白名单，非白名单来源直接拒绝（可选加固）
5. 幂等：按 merchant_order_no 查 pay_order
    已支付 → 标记日志"重复通知忽略"，返回 success
    未支付 → 乐观锁流转 10 → 20，回填 channel_trade_no / success_time / pay_amount
6. 通知业务方（**MQ 异步**，RocketMQ）：
    发送成功 → biz_notify_status=1
    发送失败 → biz_notify_status=2（定时重推，见兜底）
7. 更新 notify_count / notify_time
    │
    ▼
mall-order 消费 MQ → 更新业务订单已支付 → 扣减冻结库存
```

### 5.3 退款流程

```
mall-order 发起退款（售后审核通过）
    │
    ▼
POST /v1/pay/refund { payOrderNo, refundAmount, reason, userId }
    │
    ▼
1. 校验：支付单已支付、累计已退 + 本次 ≤ pay_amount
2. 审核判定（已确认：默认自动退款）：
    按 biz_order_no + user_id 在 pay_order 查得到该支付单 → 自动退款，跳过审核
    查不到（商品订单或退款申请人在支付订单库不存在）→ 人工审核（audit_status=1）
3. 创建 pay_refund（refund_no 雪花ID）
4. 审核通过 / 自动退款 → 渠道 refund() → 提交退款
5. 等待退款回调 / 主动查单 → refund_status → 退款成功
6. 更新支付单 refund_amount 累计 + refund_status 维度流转
7. 通知 mall-order 退款结果（**MQ 异步**）
```

### 6.2 各步骤细节

**Step 1 下载**：按渠道调用 `downloadBill(昨日, config)`，文件落 MinIO 留存，路径写入 `recon_batch.file_path`。创建批次（`uk_channel_date` 幂等）。

> 📌 **渠道对账单生成时间与下载接口（官方约束，2026-08 核实）**：
>
> - **支付宝**（接口 `alipay.data.dataservice.bill.downloadurl.query`）：对账单 **T+1 生成**（只能下载前一日 24 点前的账单），官方**不承诺具体几点生成**，建议"第二日 10:00 以后下载"。参数 `bill_type=trade`（**业务账单**，只含接口交易）；`signcustomer` 账务账单含所有余额变动（含线下转账等），会混入对不上，**不用于对账**。
> - **微信支付**（接口 `GET /v3/bill/tradebill`，普通商户）：按日生成交易账单，**"每日 10 点后生成昨日交易账单文件"**；错误码 `STATEMENT_CREATING` 表示账单生成中，**T+1 上午 10 点后可重试**。参数 `bill_date` 仅支持**三个月内**、`bill_type` 默认 `ALL`、`tar_type=GZIP` 返回压缩文件流。
> - 因此**对账定时任务设在次日 10:30**（两家保守交集），并带失败重试（间隔递增）兜住支付宝生成较晚的情况。
>
> **下载链路约束：**
> - **下载链接时效：支付宝 30 秒 / 微信 5 分钟**——「获取下载地址」和「下载文件」必须**原子化**：拿到 URL 后立刻请求，失败则重新调用接口获取新地址，不能把 URL 存库慢慢下。微信返回 `download_url`（5 分钟内有效）+ `hash_value`（SHA1，下载后校验文件一致性）。
> - **金额单位：微信账单为「元」**，支付宝为「分」——解析时统一换算为**分（bigint）**入库（`amount`/`fee`/`income`），换算只发生在解析策略内。
> - **账单文件格式**：支付宝 `csv.zip`（保存路径后缀必须是 `.zip`，否则乱码），内文编码 ANSI/GBK；微信为文本 CSV——解析策略各自处理编码。
> - **沙箱限制**：支付宝沙箱下载的账单信息为空（无实际数据），对账联调需用真实商户或人工构造账单文件。

**Step 2 解析 + 批量入库**：
- 解析 excel/csv → `List<BillRow>`（渠道策略各自实现）
- 统一转换：金额按渠道单位换算为分、交易类型归一为 PAY/REFUND
- **大批量插入**：`LOAD DATA LOCAL INFILE` 或 JDBC batch（每批 1000 条），先写临时文件再灌库，避免单条 insert 的性能瓶颈
- 批次状态 → 2 已解析入库

**Step 3 总额校验（大小款 - 第一道闸）**：

> 📌 **对账时间对齐（先读这节）**：对账拉取平台侧记录的依据是「渠道 × 时间窗」，但**渠道时间和我方时间是两个时钟、两个时刻**，绝不能拿雪花 ID 当时间边界：
>
> - **时间锚点**：平台侧唯一可靠的时间锚点是 `pay_order.success_time` / `pay_refund.success_time`（支付/退款成功落库时刻），对账窗口查询一律以这两个字段为边界；**不使用主键 ID 近似时间**。
> - **趋势递增 ≠ 时间有序**：雪花 ID 是**趋势递增**，跨 worker 生成时 ID 大小顺序与时间先后**不保证一致**（同 worker 同毫秒靠 sequence 递增、不同 worker 交错、时钟回拨还会吐出更小 ID）。因此不能用 ID 范围近似时间窗口——会包进窗口外的数据，导致漏单或误判。趋势递增的好处只在 InnoDB 插入近顺序、降低页分裂，与对账正确性无关。
> - **时间窗缓冲**：渠道交易完成时间与 `success_time` 相差几秒到几分钟（回调延迟/网络抖动）。若严格按 CSV 最早/最晚时间查，窗口边界上的交易会被误判为 `ONLY_CHANNEL`。因此平台侧按 **trade_date 整日 + 跨日缓冲**查询：`success_time` 落在 `[trade_date 00:00:00, trade_date+1 06:00:00)` 等宽松窗口，吸收延迟回调。
> - **时间只做边界、不做匹配**：时间窗只决定「加载哪些平台侧记录」，**逐笔撮合仍按 `merchant_order_no` 精确匹配**，不参与单笔相等判断。CSV 最早/最晚时间仅作合理性校验，不作硬边界。

```sql
-- 渠道侧（临时表单表聚合）
SELECT SUM(income), COUNT(*) FROM recon_temp WHERE batch_no = ?;
-- 平台侧（支付单单表聚合，无 JOIN，命中 idx_channel_success_time）
SELECT SUM(pay_amount) - SUM(refund_amount) FROM pay_order
 WHERE channel_code = ? AND success_time >= ? AND success_time < ?;
```
两个单表聚合各自独立执行，在应用层相减得到净额差异。两者差额 ≠ 0 → 批次标「有差异待处理」，进入逐笔定位。

**对账结果判定（三种情形）**：

> 前提：支付宝/微信对账单**只包含交易成功的订单**（无未支付、无失败记录）。因此我方侧也要用「已成功」的记录来对齐——`success_time` 有值（支付/退款成功落库）的 `pay_order` / `pay_refund`。对账最终收敛为三种结果：

| 结果 | 判定 | 含义 | 后果分析 |
|------|------|------|---------|
| **① 相同（对平）** | 渠道笔数 = 我方成功笔数，且渠道净额 = 我方净额 | 当日账目完全一致 | ✅ 正常。批次标「对账完成」，流程结束，无需处置 |
| **② 第三方短 / 我方长** | 渠道净额 < 我方净额（或渠道笔数更少） | 我方账上记的收款 **多于** 渠道实际收到 | ⚠️ **短款** `SHORT_PAYMENT`。我方**多记了收款**（虚记、重复记账、渠道漏单）或**少记了退款**（退款已发起但渠道未扣）。后果：账面资金虚高、账实不符；时间越久越难追查。处置：反查我方支付单是否真实发生（`biz_order_no` 反查业务订单）；虚记的做冲正/退款；漏记的补退款 |
| **③ 第三方长 / 我方短** | 渠道净额 > 我方净额（或渠道笔数更多） | 我方账上记的收款 **少于** 渠道实际收到 | 🔴 **长款** `LONG_PAYMENT`。我方**少记了收款**（回调丢失、漏记）或**多记了退款**（重复退款）。后果：渠道多收了用户的钱，我方却未入账，**资金风险最高**。处置：优先逐笔定位——回调丢失的用渠道 `trade_no` 反查补单（流转已支付 + 通知业务方）；重复退款的立即追回 |

三种结果与逐笔 `diff_type` 的映射（差额最终由逐笔差异解释）：

| 对账结果 | 对应的逐笔 diff_type | 说明 |
|---------|---------------------|------|
| ① 相同 | 无 | 全部命中且金额一致 |
| ② 第三方短 / 我方长 | `ONLY_PLATFORM`（我方有、渠道无）+ `SHORT_PAYMENT`（金额残差） | 我方多出单 / 我方净额偏高 |
| ③ 第三方长 / 我方短 | `ONLY_CHANNEL`（渠道有、我方无）+ `LONG_PAYMENT`（金额残差） | 渠道多出单 / 渠道净额偏高 |

> 处置优先级：**③ 长款（渠道多收）最高**，因为它涉及"渠道收了用户的钱我方未入账"，必须当日清零；② 短款次之，属我方内部账实不符，可次日复核。只有 ① 平账才是正常终态，② ③ 都应通过自动兜底或人工介入收敛到 ①。

**Step 4 逐笔对比（大小款 - 第二道闸，无联表）**：

> 对账逐笔对比**不做跨表 JOIN**。`recon_temp` 与 `pay_order` 同属一库时 JOIN 看似可行，但一旦 `pay_order` 分库分表（或数据量大后拆分），跨表 JOIN 会因分片键无法路由而退化成全分片广播扫描，必然出错或不可用。因此对比改为**双批查询 + 内存撮合**：

1. **批查渠道侧**：`SELECT ... FROM recon_temp WHERE batch_no = ? ORDER BY trade_no`，加载当日全部渠道明细
2. **批查平台侧**：`SELECT ... FROM pay_order WHERE channel_code = ? AND success_time >= ? AND success_time < ?`（或按 `merchant_order_no` 范围），加载对应支付单，只取撮合所需列（`merchant_order_no`、`pay_amount`、`refund_amount`、`pay_status` 等）
3. **内存撮合**：两侧各按 `trade_no`/`merchant_order_no` 建 HashMap，单次遍历按 key 匹配出「命中/仅渠道/仅平台」，逐笔产出差异结论写入 `recon_result`

```sql
-- 内存撮合的等价语义（伪代码，并非真实执行的 SQL JOIN）
for (billRow : channelSide)  hit = platformMap.get(billRow.tradeNo);
for (payOrder : platformSide) hit = channelMap.get(payOrder.merchantOrderNo);
```

| 对比结果 | diff_type | 结论 |
|---------|-----------|------|
| 平台有、渠道有、金额一致 | — | 正常，不入库 |
| 平台有、渠道有、金额不一致 | `AMOUNT_MISMATCH` | 查优惠/费率，异常介入 |
| 平台有、渠道无 | `ONLY_PLATFORM` | 我方虚记或渠道漏单 |
| 平台无、渠道有 | `ONLY_CHANNEL` | 回调丢失，需补单 |
| 两侧金额合计差异 | `LONG_PAYMENT` / `SHORT_PAYMENT` | 长款自动退款，短款追讨 |

> 📌 单表查询是后续分库分表的**前提条件**。本设计所有表在数据量大后都能独立分片：`pay_order` 可按 `user_id` 分片、`recon_temp` 按 `batch_no` 分片、`recon_result` 按 `batch_no` 分片，分片间互不跨表 JOIN。对账按「渠道 × 日期」的批次天然落在一个分片上，内存撮合在两批同分片数据间进行，无广播扫描。

**Step 5 生成结果**：每笔差异写 `recon_result`，批次统计 `diff_count / diff_total_amount`。

**Step 6 差异处理**：见下方「差异兜底」。

### 6.3 对账差异兜底措施

| 差异类型 | 自动兜底 | 人工兜底 |
|---------|---------|---------|
| `LONG_PAYMENT` 长款 | 渠道多收（本地少记）→ 金额可对到某笔已支付单时自动发起退款 | 对不上单时人工介入 |
| `SHORT_PAYMENT` 短款 | 渠道少收（本地多记）→ 记录差异单，联系渠道 | 渠道对账异议流程 |
| `AMOUNT_MISMATCH` | 核对优惠金额/手续费；无法解释则告警 | 财务人工核对 |
| `ONLY_PLATFORM` | 反查 `biz_order_no` 业务订单是否真实下单且我方确已改已支付——若业务单也存在，则是我方记了渠道没收，**发起退款** | 业务侧确认 |
| `ONLY_CHANNEL` | 渠道有单平台无 → 极可能是**回调丢失**：用 `trade_no` 反查 `pay_order`（可能本地有单但状态没流转）；确认用户真实支付后**补单**（流转已支付 + 通知业务方） | 无法反查到单时人工 |
| `FEE_MISMATCH` | 费率变更核对 | 与渠道确认 |
| `STATUS_MISMATCH` | 如平台已支付、渠道已退款 → 补做退款流程 | 人工介入 |

**全局兜底：**
0. **总额先行分治**：对账以「渠道总净额 vs 我方总净额」差异**是否为零**作为总开关——差额为零直接判对平（无需逐笔）；差额非零才进逐笔定位，并按「第三方长/第三方短」两大方向分别走 `LONG_PAYMENT` / `SHORT_PAYMENT` 处置链路，避免在平账日浪费逐笔资源。
1. **回调幂等**：`pay_notify_log` 先落库 + 乐观锁前置状态校验，重复回调无害
2. **主动查单轮询**：`pay_order` 中 `pay_status IN (10)` 且创建超过 5 分钟的订单，定时（如每 5 分钟）向渠道 `query()`，防止回调永久丢失；超过 15 分钟仍未查到且渠道无单 → 标记待关单
3. **业务方通知补偿**：`biz_notify_status=2` 的支付单，定时重推（退避重试：1min/5min/15min/1h，最多 5 次），防止业务订单卡在待支付
4. **超时关单**：`expire_time` 过期未支付的支付单，定时（如每 10 分钟）扫描关闭（`30 已关闭`），释放库存/优惠；`expire_time` 创建支付单时设置（默认 30 分钟，可配置）
5. **对账批次幂等**：`uk_channel_date` + 状态检查；重复执行先删旧临时表数据再重建，不产生脏数据
6. **临时表保留期**：`recon_temp` 对账完成保留 N 天（建议 7 天）后按 `batch_no` 清理，`recon_result` 长期保留
7. **对账失败降级与重试窗口**：下载/解析失败 → 批次标失败 + 告警。重试采用**间隔递增**（支付宝生成时间不固定，可能晚于 10:30；微信 API 仅支持下载 3 个月内账单）——当日未成的批次需在**次日同一任务窗口内重试**，若连续多日失败需人工介入，避免超过微信 3 个月下载时限导致历史账单永久缺失
8. **对账单文件归档**：MinIO 留存原件，支持随时复盘
9. **支付宝下载链接 30 秒时效**：获取下载地址后必须**立即下载**（原子操作）；超时则重新调用接口获取新地址，不做"先存 URL 后下载"的异步化
10. **对账金额容差**：金额差异在容差范围内（如 ≤ 0.01 元，四舍五入/分单位换算误差）视为对平，不触发差异告警；超过容差才进差异处理。容差阈值可配置
11. **告警通道（待实现阶段细化）**：对账差异、回调连续失败、退款失败、超时关单异常、渠道配置失效等场景触发告警。通道：邮件 / 钉钉/企微群机器人 / 短信（按严重级别分发）；对账差异 → 财务群，资金风险（长款）→ 最高级别人工介入。
