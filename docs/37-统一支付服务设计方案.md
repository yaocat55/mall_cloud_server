# 统一支付服务设计方案

## 背景

当前 `mall-pay` 模块是**模拟支付**，存在以下问题：

- 只有一个 `mockPay` 接口，收到前端传来的订单号后，直接改订单状态为已支付，无任何真实支付行为
- 没有自己的数据库，唯一的外部数据源是 mall-order 的 Feign 查询
- `PayStatusEnum` 只有 4 个状态（待支付/已支付/已退款/失败），无法表达真实支付链路中的中间态（支付中、已关闭、退款中、部分退款等）
- `PayService.mockPay` 直接持有 `orderFeignClient`，依赖方向是 mall-pay → mall-order；而 mall-order 又通过 `PayFeignClient` 调用 mall-pay，**已存在循环依赖隐患**
- 渠道集成只有 Alipay 一种雏形，无法扩展微信支付、微信小程序支付及未来其他国内支付渠道

目标：将 mall-pay 改造为**统一支付服务**——拥有自己的数据库，聚合支付宝/微信支付/微信小程序支付等移动端支付渠道，设计可扩展的多渠道架构，并配套一套**每日对账系统**（拉取渠道对账单 → 解析 → 大批量入临时表 → 与本地支付订单对比 → 大小款计算 → 差异结论 → 兜底措施），使其日后可作为独立支付服务接入其他项目。

## 一、架构

### 1.1 微服务边界（改造后）


### 1.2 关键决策

| 决策点 | 结论 | 理由 |
|--------|------|------|
| 数据库 | 独立 `cloud_mall_pay`，单库不分片 | 支付数据量适中，不需要分库分表；ShardingSphere 留给订单 |
| 金额单位 | **分（bigint）** | 所有国内支付 SDK 金额均以分为单位；对账需要精确加减避免浮点误差；与 `decimal` 相比省空间、无精度问题 |
| ID 生成 | 雪花 ID（common-workid） | 与项目其他模块一致；支付单号、退款单号、对账批次号均由服务生成 |
| 并发控制 | 乐观锁 `version` | 状态流转（回调/退款/对账）用 `UPDATE ... SET status=?, version=version+1 WHERE id=? AND version=?` 防止重复处理 |
| 审计字段 | `create_user_id/create_user_name/create_time/update_user_id/update_user_name/update_time` | 与项目 `FillUserUtil` / `BaseEntity` 规范一致 |
| 渠道扩展 | 策略模式 `PayChannelStrategy` | 新增渠道 = 新增一个策略实现 + 一张渠道配置，不改核心流程 |
| 业务解耦 | 支付成功用 **MQ 或 Feign** 通知业务方，pay 服务不再依赖 order-client | 消除现有循环依赖；支持多业务方（未来其他项目） |

### 1.3 渠道抽象

**官方 SDK 版本（2025-07 核实）：**

| 渠道 | Maven 坐标 | 最新版本 | 发布日期 | 说明 |
|------|-----------|---------|---------|------|
| 支付宝 | `com.alipay.sdk:alipay-sdk-java` | `4.40.272.ALL` | 2025-06-24 | 网关聚合版，覆盖 App 支付/手机网站支付等全部场景 |
| 微信支付 | `com.github.wechatpay-apiv3:wechatpay-java` | `0.2.17` | 2025-04-11 | APIv3 协议，一套代码覆盖 JSAPI（小程序）/APP/Native |

统一接口 `PayChannelStrategy`，各渠道实现，**本次设计先行约定接口，具体实现分阶段落地**：

```java
public interface PayChannelStrategy {
    /** 渠道编码：ALIPAY / WECHAT_PAY / WECHAT_MINI */
    String channelCode();

    /** 创建支付单，返回拉起支付所需参数（调起 SDK 的 json/字符串） */
    PayPrepayResult prepay(PayOrder payOrder, PayChannelConfig config);

    /** 主动查询订单状态（兜底轮询用） */
    PayQueryResult query(String merchantOrderNo, PayChannelConfig config);

    /** 关闭未支付订单 */
    boolean close(String merchantOrderNo, PayChannelConfig config);

    /** 申请退款 */
    RefundResult refund(PayRefund refund, PayChannelConfig config);

    /** 查询退款结果 */
    RefundQueryResult queryRefund(String refundNo, PayChannelConfig config);

    /** 回调报文验签 */
    boolean verifyNotify(Map<String, String> params, String rawBody, PayChannelConfig config);

    /** 解析回调报文为统一对象 */
    PayNotifyMessage parseNotify(String rawBody, PayChannelConfig config);

    /** 下载对账单，返回文件内容 */
    byte[] downloadBill(LocalDate tradeDate, PayChannelConfig config);

    /** 解析对账单 → 统一账单行结构 */
    List<BillRow> parseBill(byte[] content);
}
```

## 二、数据库设计（cloud_mall_pay）

共 **7 张表**：业务侧 4 张（pay_order / pay_notify_log / pay_refund / pay_channel_config），对账侧 3 张（recon_batch / recon_temp / recon_result）。

### 2.1 pay_order 支付订单表（核心）

一笔业务订单对应**一条支付订单**（支持一单多支付单场景：支付单过期后重新发起，业务订单不变）。

```sql
CREATE DATABASE IF NOT EXISTS `cloud_mall_pay` DEFAULT CHARSET utf8mb4;

CREATE TABLE `cloud_mall_pay`.`pay_order` (
    `id`                 bigint       NOT NULL              COMMENT '主键，雪花ID',
    `pay_order_no`       varchar(32)  NOT NULL              COMMENT '支付订单号（对外交易号，雪花ID字符串）',
    `biz_order_no`       varchar(64)  NOT NULL              COMMENT '业务方订单号（如商城 tradeCode）',
    `biz_type`           varchar(32)  NOT NULL              COMMENT '业务类型：MALL_ORDER 商城订单 / OTHER 其他',
    `channel_code`       varchar(16)  NOT NULL              COMMENT '支付渠道：ALIPAY / WECHAT_PAY / WECHAT_MINI',
    `merchant_order_no`  varchar(64)  NOT NULL              COMMENT '渠道商户订单号（本地唯一，渠道侧可回溯）',
    `channel_trade_no`   varchar(64)          DEFAULT NULL   COMMENT '渠道交易号（回调成功后回填）',
    `user_id`            bigint       NOT NULL              COMMENT '用户ID',
    `open_id`            varchar(64)          DEFAULT NULL   COMMENT '微信 openId（小程序支付必填）',
    `subject`            varchar(128) NOT NULL              COMMENT '商品描述（收银台展示）',
    `body`               varchar(512)         DEFAULT NULL   COMMENT '商品详情',
    `total_amount`       bigint       NOT NULL              COMMENT '订单总金额（单位：分）',
    `pay_amount`         bigint       NOT NULL              COMMENT '实际支付金额（单位：分，默认=total_amount）',
    `refund_amount`      bigint       NOT NULL DEFAULT 0    COMMENT '已退款金额（单位：分）',
    `currency`           varchar(8)   NOT NULL DEFAULT 'CNY' COMMENT '币种',
    `pay_status`         tinyint      NOT NULL DEFAULT 10   COMMENT '支付状态：见状态机',
    `refund_status`      tinyint      NOT NULL DEFAULT 0    COMMENT '退款状态：0无 1退款中 2部分退款 3全额退款 4退款失败',
    `notify_count`       int          NOT NULL DEFAULT 0    COMMENT '渠道回调次数',
    `notify_time`        datetime(3)          DEFAULT NULL   COMMENT '最近一次回调时间',
    `biz_notify_status`  tinyint      NOT NULL DEFAULT 0    COMMENT '业务方通知状态：0待通知 1通知成功 2通知失败',
    `client_ip`          varchar(64)          DEFAULT NULL   COMMENT '客户端IP',
    `device_info`        varchar(128)         DEFAULT NULL   COMMENT '设备信息',
    `success_time`       datetime(3)          DEFAULT NULL   COMMENT '支付成功时间',
    `expire_time`        datetime(3)          DEFAULT NULL   COMMENT '支付过期时间（超时自动关闭）',
    `closed_time`        datetime(3)          DEFAULT NULL   COMMENT '关闭时间',
    `version`            int          NOT NULL DEFAULT 0    COMMENT '乐观锁',
    `create_user_id`     bigint       NOT NULL              COMMENT '创建人ID',
    `create_user_name`   varchar(64)  NOT NULL              COMMENT '创建人姓名',
    `create_time`        datetime(3)  NOT NULL              COMMENT '创建时间',
    `update_user_id`     bigint       NOT NULL              COMMENT '更新人ID',
    `update_user_name`   varchar(64)  NOT NULL              COMMENT '更新人姓名',
    `update_time`        datetime(3)  NOT NULL              COMMENT '更新时间',
    `remark`             varchar(255)         DEFAULT NULL   COMMENT '备注',
    UNIQUE KEY `uk_pay_order_no` (`pay_order_no`),
    UNIQUE KEY `uk_merchant_order_no` (`merchant_order_no`),
    KEY `idx_biz_order` (`biz_type`, `biz_order_no`),
    KEY `idx_user_id` (`user_id`),
    KEY `idx_channel_trade_no` (`channel_code`, `channel_trade_no`),
    KEY `idx_pay_status_create_time` (`pay_status`, `create_time`),
    KEY `idx_expire_time` (`expire_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付订单表';
```

**字段设计要点：**

- **`merchant_order_no` 与 `pay_order_no` 双号**：`pay_order_no` 是支付服务对外暴露的业务号；`merchant_order_no` 是提交给渠道的商户订单号（各渠道对商户订单号格式有约束，如微信限制 6-32 位字母数字）。两者都唯一，渠道对账单/回调里带的是 `merchant_order_no`，用于回溯 `pay_order_no`。
- **`biz_order_no` + `biz_type`**：绑定业务订单，用于可追溯。对账时如果渠道侧出现的订单本地没有，用 `biz_order_no` 反查业务方订单确认是否真实发生交易。
- **金额分三份**：`total_amount`（应付）、`pay_amount`（实付，渠道优惠可能导致实付≠应付）、`refund_amount`（已退累计）。对账"大小款"对比以 `pay_amount` 为准。
- **`pay_status` / `refund_status` 拆开**：一个订单可以"已支付 + 部分退款"，单一状态字段表达不了，所以拆两个维度。
- **`notify_count` / `notify_time` / `biz_notify_status`**：渠道回调幂等、业务方通知补偿的支撑字段。

### 2.2 pay_notify_log 回调日志表

渠道回调**必须先落库再处理**，防止验签/处理中途异常导致报文丢失，同时为审计留痕。

```sql
CREATE TABLE `cloud_mall_pay`.`pay_notify_log` (
    `id`               bigint       NOT NULL PRIMARY KEY  COMMENT '主键，雪花ID',
    `pay_order_id`     bigint       NOT NULL              COMMENT '支付订单ID',
    `pay_order_no`     varchar(32)  NOT NULL              COMMENT '支付订单号',
    `channel_code`     varchar(16)  NOT NULL              COMMENT '渠道编码',
    `channel_trade_no` varchar(64)          DEFAULT NULL   COMMENT '渠道交易号',
    `notify_type`      varchar(16)  NOT NULL              COMMENT '通知类型：PAY 支付 / REFUND 退款',
    `raw_data`         text         NOT NULL              COMMENT '渠道原始报文',
    `decrypt_data`     text                DEFAULT NULL   COMMENT '解密后报文（微信需要解密）',
    `verify_status`    tinyint      NOT NULL DEFAULT 0    COMMENT '验签结果：0未验证 1成功 2失败',
    `process_status`   tinyint      NOT NULL DEFAULT 0    COMMENT '处理状态：0待处理 1处理成功 2处理失败 3重复通知忽略',
    `process_msg`      varchar(512)         DEFAULT NULL   COMMENT '处理结果信息',
    `create_time`      datetime(3)  NOT NULL              COMMENT '创建时间',
    KEY `idx_pay_order_id` (`pay_order_id`),
    KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='支付渠道回调日志';
```

**设计要点：** `uk_channel_trade_date` 保证同一渠道同一天只对账一次；任务幂等——重复执行先检查批次状态，已完成的直接跳过（或删除重建，见兜底）。

### 2.6 recon_temp 对账临时表（核心）

**对账临时表的设计目标：** 渠道对账单（excel/csv）解析后**大批量插入**，然后与本地 `pay_order` 表做关联对比。设计上要满足：

1. **可批量灌入**：字段扁平、宽表，支持 `LOAD DATA` 或批量 `INSERT`
2. **多渠道兼容**：支付宝/微信/小程序对账单字段各异，用「通用字段 + ext_json 扩展列」吸收差异
3. **按批次隔离**：`batch_no` 区分不同批次数据，同表复用，无需物理建表
4. **保留期可清理**：对账完成保留 N 天便于排查，之后批量删除

```sql
CREATE TABLE `cloud_mall_pay`.`recon_temp` (
    `id`                bigint       NOT NULL AUTO_INCREMENT  COMMENT '自增主键（临时表专用，非雪花）',
    `batch_no`          varchar(32)  NOT NULL                 COMMENT '对账批次号',
    `line_no`           int          NOT NULL                 COMMENT '文件行号',
    `trade_no`          varchar(64)  NOT NULL                 COMMENT '渠道商户订单号（= merchant_order_no）',
    `channel_trade_no`  varchar(64)           DEFAULT NULL    COMMENT '渠道交易流水号',
    `refund_no`         varchar(64)           DEFAULT NULL    COMMENT '渠道退款单号（退款记录行才有）',
    `trade_time`        datetime     NOT NULL                 COMMENT '交易时间',
    `trade_type`        varchar(16)  NOT NULL                 COMMENT '交易类型：PAY 支付 / REFUND 退款',
    `amount`            bigint       NOT NULL                 COMMENT '交易金额（分，正数）',
    `fee`               bigint       NOT NULL DEFAULT 0       COMMENT '手续费（分）',
    `income`            bigint       NOT NULL DEFAULT 0       COMMENT '净入账金额（分，amount - fee，可正可负）',
    `trade_status`      varchar(16)           DEFAULT NULL    COMMENT '渠道交易状态：SUCCESS/REFUND/CLOSED',
    `payer_account`     varchar(64)           DEFAULT NULL    COMMENT '付款方账号',
    `ext_json`          json                  DEFAULT NULL    COMMENT '渠道特有字段（原样保留）',
    `create_time`       datetime(3)  NOT NULL                 COMMENT '入库时间',
    PRIMARY KEY (`id`),
    KEY `idx_batch_no` (`batch_no`),
    KEY `idx_batch_trade_no` (`batch_no`, `trade_no`),
    KEY `idx_batch_trade_time` (`batch_no`, `trade_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='对账临时表（按批次批量插入，对账完成保留N天后清理）';
```

**「大小款对比」的核心依托：** 对账时用 `SUM(income)` 得到**渠道侧净额**，用 `SUM(pay_amount) - SUM(refund_amount)` 得到**平台侧净额**，两者相减即长款/短款总额。逐笔对比用临时表与 `pay_order` 按 `trade_no = merchant_order_no` 关联。

### 2.7 recon_result 对账结果表（逐笔差异）

每笔交易一个对比结论，差异行进入人工/自动处理流。

```sql
CREATE TABLE `cloud_mall_pay`.`recon_result` (
    `id`               bigint       NOT NULL PRIMARY KEY  COMMENT '主键，雪花ID',
    `batch_no`         varchar(32)  NOT NULL              COMMENT '对账批次号',
    `channel_code`     varchar(16)  NOT NULL              COMMENT '渠道编码',
    `trade_no`         varchar(64)  NOT NULL              COMMENT '渠道商户订单号',
    `channel_trade_no` varchar(64)          DEFAULT NULL   COMMENT '渠道交易号',
    `pay_order_id`     bigint                DEFAULT NULL   COMMENT '本地支付订单ID',
    `pay_order_no`     varchar(32)           DEFAULT NULL   COMMENT '本地支付订单号',
    `trade_time`       datetime              DEFAULT NULL   COMMENT '交易时间',
    `platform_amount`  bigint       NOT NULL DEFAULT 0    COMMENT '平台侧金额（分，退款记负）',
    `channel_amount`   bigint       NOT NULL DEFAULT 0    COMMENT '渠道侧金额（分，退款记负）',
    `diff_type`        varchar(32)  NOT NULL              COMMENT '差异类型：见下方枚举',
    `diff_amount`      bigint       NOT NULL DEFAULT 0    COMMENT '差异金额（分，带方向）',
    `handle_status`    tinyint      NOT NULL DEFAULT 0    COMMENT '处理状态：0待处理 1处理中 2已处理 3无需处理',
    `handle_type`      tinyint                DEFAULT NULL COMMENT '处理方式：1自动冲正 2自动退款 3自动补单 4人工处理',
    `handle_result`    varchar(512)          DEFAULT NULL   COMMENT '处理结果说明',
    `handle_user_id`   bigint                DEFAULT NULL   COMMENT '处理人ID',

    `version`          int          NOT NULL DEFAULT 0    COMMENT '乐观锁',

    `update_time`      datetime(3)  NOT NULL              COMMENT '更新时间',

    KEY `idx_handle_status` (`handle_status`),

```

**差异类型枚举 `diff_type`：**

| 枚举 | 含义 | 方向 |
|------|------|------|
| `LONG_PAYMENT` | 长款：渠道净额 > 平台净额（我方少记收款） | 渠道多 |
| `SHORT_PAYMENT` | 短款：渠道净额 < 平台净额（我方多记收款） | 渠道少 |

## 三、支付状态机

### 3.1 支付状态 pay_status

```
                    ┌─────────┐
                    │ 10 待支付 │◄──────────────┐ 超时/取消后重发支付单
                    └────┬────┘                │
                         │ 调起支付             │
                         ▼                     │
                    ┌─────────┐                │
                    │ 20 支付中 │               │
                    └────┬────┘                │
          ┌──────────────┼──────────────┐      │
          │回调成功        │主动查单成功     │      │
          ▼              ▼              ▼      │
    ┌─────────┐   ┌─────────┐    ┌─────────┐  │
    │ 30 已支付 │   │ 40 已关闭 │    │ 50 支付失败│ │
    └────┬────┘   └─────────┘    └─────────┘  │
         │ 超时未付/用户取消                      │
         ▼                                     │
    重新发起支付（新建 pay_order）────────────────┘
```

- 支付状态只关心「收钱」；收完钱之后的退款，走 `refund_status` 维度，**不回退 pay_status**
- `30 已支付` 是终态之一；`40 已关闭`（超时/取消）可重新发起新的支付单（业务订单不变）
- 从 `10 待支付` 到 `20 支付中` 由「调起渠道」触发；从 `20` 到 `30` 由**渠道回调或主动查单**确认，不做本地乐观判定

### 3.2 退款状态 refund_status（支付单维度）

```
            0 无退款
            │ 发起第一笔退款
            ▼
    ┌─────────────────┐   渠道退款成功(部分)   ┌──────────────┐
    │ 1 退款中         │ ────────────────────►│ 2 部分退款     │
    └────────┬────────┘                       └──────────────┘
             │ 渠道退款成功(累计=pay_amount)
             ▼
    ┌──────────────┐
    │ 3 全额退款    │
    └──────────────┘
    退款失败 → 4 退款失败（可重试，从 pay_refund.refund_status 流转）
```

### 3.3 退款单状态（pay_refund 维度）

```
0 待处理 → 1 处理中（已提交渠道） → 2 退款成功
                          ↘ 3 退款失败（可重新发起退款单）
审核（如配置需审核）：0 无需审核 / 1 待审核 / 2 审核通过 / 3 审核拒绝
```

### 3.4 状态流转的并发控制

所有状态变更统一走乐观锁：

```sql
UPDATE pay_order
   SET pay_status = #{target}, version = version + 1, update_time = NOW()
 WHERE id = #{id} AND version = #{expectVersion}
   AND pay_status IN (#{fromStatuses})   -- 前置状态约束
```

回调处理时 `fromStatuses` 限定 `(10, 20)` → 回调幂等，重复回调命中 `30` 直接跳过。退款累计额更新同样带 `version` 和「已退金额+本次 ≤ pay_amount」约束。

## 四、核心流程

### 4.1 创建支付单（mall-order → mall-pay）

```
mall-order 下单成功（业务订单=WAIT_PAY）
    │
    ▼
POST /v1/pay/create  { bizOrderNo, bizType, channelCode, subject, totalAmount, userId, openId? }
    │
    ▼
1. 校验：渠道已启用、金额>0、同 bizOrderNo 未存在进行中支付单
2. 生成 pay_order（雪花ID 主键、pay_order_no、merchant_order_no）
3. 渠道 prepay() → 返回拉起支付参数（支付宝参数串 / 微信预支付单 sign）
4. 返回 { payOrderNo, prepayParams }
    │
    ▼
前端收银台调起支付
```

### 4.2 支付回调处理（渠道 → mall-pay → mall-order）

```
渠道异步通知
    │
    ▼
1. 先落 pay_notify_log（原始报文不丢）
2. 验签：
    成功 → 继续
    失败 → 返回失败给渠道，渠道会重试
3. 幂等：按 merchant_order_no 查 pay_order
    已支付 → 标记日志"重复通知忽略"，返回 success
    未支付 → 乐观锁流转 10/20 → 30，回填 channel_trade_no / success_time / pay_amount
4. 通知业务方（MQ 或 Feign）：
    成功 → biz_notify_status=1
    失败 → biz_notify_status=2（定时重推，见兜底）
5. 更新 notify_count / notify_time
    │
    ▼
mall-order 收到支付成功通知 → 更新业务订单已支付 → 扣减冻结库存
```

### 4.3 退款流程

```
mall-order 发起退款（售后审核通过）
    │
    ▼
POST /v1/pay/refund { payOrderNo, refundAmount, reason }
    │
    ▼
1. 校验：支付单已支付、累计已退 + 本次 ≤ pay_amount
2. 创建 pay_refund（refund_no 雪花ID）
3. 渠道 refund() → 提交退款
4. 等待退款回调 / 主动查单 → refund_status → 退款成功
5. 更新支付单 refund_amount 累计 + refund_status 维度流转
6. 通知 mall-order 退款结果
```

## 五、对账系统设计（核心）

### 5.1 对账时序（每日）

```
┌──────────────┐   ┌──────────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ 定时任务 00:30 │──►│ 1. 下载对账单      │──►│ 2. 解析 + 批量入库 │──►│ 3. 总额校验        │
│ (xxl-job/内置) │   │  按渠道×昨日下载    │   │  写 recon_temp    │   │  渠道SUM vs 平台SUM │
└──────────────┘   └──────────────────┘   └──────────────────┘   └────────┬─────────┘
                                                                          │
              ┌──────────────────┐   ┌──────────────────┐   ┌─────────────▼─────────┐
              │ 6. 差异处理        │◄──│ 5. 生成 recon_result│◄──│ 4. 逐笔对比           │
              │  自动兜底 + 人工     │   │  每笔一个结论       │   │  temp ⟕ pay_order    │
              └──────────────────┘   └──────────────────┘   └───────────────────────┘
```

### 5.2 各步骤细节

**Step 1 下载**：按渠道调用 `downloadBill(昨日, config)`，文件落 MinIO 留存，路径写入 `recon_batch.file_path`。创建批次（`uk_channel_date` 幂等）。

**Step 2 解析 + 批量入库**：
- 解析 excel/csv → `List<BillRow>`（渠道策略各自实现）
- 统一转换：金额按渠道单位换算为分、交易类型归一为 PAY/REFUND
- **大批量插入**：`LOAD DATA LOCAL INFILE` 或 JDBC batch（每批 1000 条），先写临时文件再灌库，避免单条 insert 的性能瓶颈
- 批次状态 → 2 已解析入库

**Step 3 总额校验（大小款 - 第一道闸）**：
```sql
-- 渠道侧
SELECT SUM(income), COUNT(*) FROM recon_temp WHERE batch_no = ?;
-- 平台侧（对账日内的支付成功 + 退款成功）
SELECT SUM(pay_amount) - SUM(refund_amount) FROM pay_order
 WHERE channel_code = ? AND success_time >= ? AND success_time < ?;
```
两者差额 ≠ 0 → 批次标「有差异待处理」，进入逐笔定位。

**Step 4 逐笔对比（大小款 - 第二道闸）**：
```sql
-- 全外连接效果：LEFT JOIN 拿"平台有渠道无"，RIGHT JOIN 拿"渠道有平台无"
SELECT t.trade_no, t.amount AS channel_amt, o.pay_amount AS platform_amt, ...
  FROM recon_temp t
  LEFT JOIN pay_order o ON t.trade_no = o.merchant_order_no;
```

| 对比结果 | diff_type | 结论 |
|---------|-----------|------|
| 平台有、渠道有、金额一致 | — | 正常，不入库 |
| 平台有、渠道有、金额不一致 | `AMOUNT_MISMATCH` | 查优惠/费率，异常介入 |
| 平台有、渠道无 | `ONLY_PLATFORM` | 我方虚记或渠道漏单 |
| 平台无、渠道有 | `ONLY_CHANNEL` | 回调丢失，需补单 |
| 两侧金额合计差异 | `LONG_PAYMENT` / `SHORT_PAYMENT` | 长款自动退款，短款追讨 |

**Step 5 生成结果**：每笔差异写 `recon_result`，批次统计 `diff_count / diff_total_amount`。

**Step 6 差异处理**：见下方「差异兜底」。

### 5.3 对账差异兜底措施

| 差异类型 | 自动兜底 | 人工兜底 |
|---------|---------|---------|
| `LONG_PAYMENT` 长款 | 渠道多收（本地少记）→ 金额可对到某笔已支付单时自动发起退款 | 对不上单时人工介入 |
| `SHORT_PAYMENT` 短款 | 渠道少收（本地多记）→ 记录差异单，联系渠道 | 渠道对账异议流程 |
| `AMOUNT_MISMATCH` | 核对优惠金额/手续费；无法解释则告警 | 财务人工核对 |
| `ONLY_PLATFORM` | 反查 `biz_order_no` 业务订单是否真实下单且我方确已改已支付——若业务单也存在，则是我方记了渠道没收，**发起退款** | 业务侧确认 |
| `ONLY_CHANNEL` | 渠道有单平台无 → 极可能是**回调丢失**：用 `trade_no` 反查 `pay_order`（可能本地有单但状态没流转）；确认用户真实支付后**补单**（流转已支付 + 通知业务方） | 无法反查到单时人工 |
| `FEE_MISMATCH` | 费率变更核对 | 与渠道确认 |
| `STATUS_MISMATCH` | 如平台已支付、渠道已退款 → 补做退款流程 | 人工介入 |

**全局兜底：**
1. **回调幂等**：`pay_notify_log` 先落库 + 乐观锁前置状态校验，重复回调无害
2. **主动查单轮询**：`pay_order` 中 `pay_status IN (10,20)` 且超时的订单，定时向渠道 `query()`，防止回调永久丢失
3. **业务方通知补偿**：`biz_notify_status=2` 的支付单，定时重推（退避重试），防止业务订单卡在待支付
4. **超时关单**：`expire_time` 过期未支付的支付单，定时关闭（`40 已关闭`），释放库存/优惠
5. **对账批次幂等**：`uk_channel_date` + 状态检查；重复执行先删旧临时表数据再重建，不产生脏数据
6. **临时表保留期**：`recon_temp` 对账完成保留 N 天（建议 7 天）后按 `batch_no` 清理，`recon_result` 长期保留
7. **对账失败降级**：下载/解析失败 → 批次标失败 + 告警，次日重试或人工触发；不影响当日支付主流程
8. **对账单文件归档**：MinIO 留存原件，支持随时复盘

## 八、待确认事项（审阅重点）

1. **金额单位**：本方案统一用**分（bigint）**。项目现有订单表用的是 `decimal`，若坚持与订单表风格一致，改为 `decimal(10,2)` 亦可，但对账计算需 `CAST` 避免精度问题。**请确认采用哪种。**
2. **业务方通知方式**：支付成功通知 mall-order，用 **MQ（RocketMQ，项目已用于库存超时释放）** 还是 **Feign 同步调用**？MQ 更解耦，Feign 更简单。**请确认。**
3. **支付/退款回调地址**：渠道侧 `notify_url` 走 BFF 还是网关直连 pay 服务？渠道回调是外部请求，需在网关放行或独立端口，**涉及网关白名单配置**，需确认。
4. **对账文件存储**：对账单原件存 MinIO（建议）。项目已有 MinIO，确认使用。
5. **对账触发方式**：内置 `@Scheduled` 还是接入 xxl-job？项目现无统一调度中心，建议先内置定时，后续再迁。
6. **是否需要退款审核环节**：本方案做了 `audit_status` 支持（默认无需审核），是否启用由业务定。
7. **多渠道商户号规划**：微信支付（App）与微信小程序支付是否同一商户号？影响 `pay_channel_config` 数据初始化。
8. **是否保留与 mall-order 的现有 Feign 依赖**：改造后 mall-pay 不应再依赖 mall-order-client（消除循环依赖），需确认 mall-order 的改造排期。
9. **支付状态 20「支付中」是否需要**：若产品上不需要区分「待支付/支付中」，可合并为单一待支付态，表结构不变，仅状态机简化。
